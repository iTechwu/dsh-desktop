# 03 · 实施路线与风险

## 阶段划分（估算为单人净工时）

### 阶段 0 · 准备（半天）

1. sso.dofe.ai：`apps/api/scripts/oauth-clients.config.ts` 注册 `sensteed-desktop`（public、PKCE、`http://127.0.0.1:*` loopback、scope 含 `offline_access`），跑 seed 落库；生产与 my-server profile 各确认 secret 映射（public client 可无 secret）。
2. 与飞书开放平台确认：现用 connector 的应用对 sensteed 企业租户可见；记录 `tenant_key`（P2 白名单用）。
3. docker-helm.dofe.ai：按契约在 `AGENTS.md` 登记新端点与 client（本地改 → 校验 → 中文 commit → push → Jenkins）。

### 阶段 1 · MVP 闭环（约 1 周）

1. **models**（1~2 天）：`desktop-auth-api` 模块（provision 端点 + contracts + ensure 复用 + 单测）；本地 `pnpm test` + `corepack pnpm build` 过门禁。
2. **桌面**（3~5 天）：
   - Host：`dofe-auth-service.ts`（状态机 + 一次性 loopback 监听 + token 交换 + 静默续期）、`dofe-auth-route.ts`（4 条路由 + permitted 栅栏）、`index.ts` 注册。
   - Client：`DofeLoginSection.tsx` + `dofe-access.ts` 文案键 + 品牌分支（sensteed 默认登录，yootun 不变）。
   - 设置 schema：`authMode` / `identity` 字段；提交顺序保持"授权最后提交"。
   - 测试：fail-closed / 不回显 / 跨源拒绝 / 会话超时 / 轮询取消，仿现有两份 spec。
3. 联调验收（0.5 天）：`corepack pnpm dev` 起桌面，真实飞书扫码走通全流程；yootun 品牌回归验证激活流程不变（`BRAND=yootun corepack pnpm dev`）。

### 阶段 2 · 组织架构与权限（约 1 周，可并行）

1. **SSO**（2~3 天）：飞书通讯录集成（contact API 拉用户部门，登录时或定时同步），access/id_token 注入 `groups`（部门 ID）+ `group_names`；`ConnectorConfig` 增加 `allowTenantKeys` 白名单。
2. **knowledge**（1 天）：确认 `KNOWLEDGE_SSO_GROUP_CLAIMS` 消费新 claim；`team.<部门ID>` 空间展示名映射；**新增成员对账 cron**（消除"只增不减"漂移风险）。
3. **桌面**（1 天）：entitlements 由 groups 映射（provision 响应计算或桌面端按 groups 映射表裁剪）；设置页插件列表展示来源标注。
4. **OpenMontage**（0.5 天）：`mcp_gateway_auth.py` `gateway_attribution()` 补读 `X-Dofe-Member-Id` → `employee_id`，按人作业统计。

### 阶段 3 · 治理深化（按需）

1. tools.dofe.ai：生产开 `MCP_GATEWAY_ONLY=true`，`McpGatewayIdentityMiddleware` 消费 Principal/Member-Id，域级 → 工具级 entitlement 过滤；调用事件落库。
2. models：key 轮换端点 + 长期 key → 短期委托 key（`runtime_delegation`）灰度。
3. 桌面：登录态展示（头像/部门）、多团队切换（如山子下多 team）。
4. 飞书文档导入 knowledge（connector worker，消费 `knowledge.source.sync.requested` outbox，框架已留）。

## 依赖顺序

```
阶段0(SSO client) ──→ 阶段1(models 端点 ∥ 桌面模块) ──→ 联调
                              └─→ 阶段2(SSO groups → knowledge/entitlements/montage) ──→ 阶段3
```

## 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| R1 | SSO social 回调体系与桌面 loopback 流并存，误用 `/auth/oauth/feishu`（写死 302 回 web） | 桌面只走 `/oauth/authorize`；联调用例覆盖"浏览器最终停在 loopback 页" |
| R2 | loopback 端口冲突 / 端口被注册表精确匹配卡住 | 监听 127.0.0.1 动态端口；SSO 治理层已放行 `http://127.0.0.1:*`，注册时按其规则登记；seed 后用 `scripts/check-oauth-client-config.js` 校验 |
| R3 | provision 端点被滥用（拿任意 SSO token 换 key） | 仅山子租户成员可签（`tenant_mismatch` 拒绝）+ 限流 + 审计 + 响应 no-store；P2 叠加飞书 tenant_key 白名单 |
| R4 | 用户多团队/跨租户导致 key 绑错租户 | P1 锁定山子单租户（品牌即租户）；多团队选择作为 P3（SSO Team 选择流程，禁 `X-Team-Id` 头，遵循 0901 契约） |
| R5 | key 泄漏（本机文件被读） | `.credentials.yaml` 0600/0700 + 文件锁已是现有基线；P2 提供轮换端点与"Web 吊销 → 下次登录自动重签"路径；高敏场景切 delegation key |
| R6 | yootun 回归被波及 | 品牌分支隔离 + 不 bump `validationVersion`；阶段 1 验收包含 yootun 全流程回归；tests 断言 yootun 分支不加载新路由 |
| R7 | knowledge 成员资格漂移（调岗/离职不回收） | 阶段 2 对账 cron 为**必做项**，不是可选 |
| R8 | 异步 MCP 工具对用户 key 返回 `MODEL_RUNTIME_CREDENTIAL_REQUIRED`（tools 现状） | 阶段 1 验收清单明确"sensteed 首发插件集避开异步 run 类域"；阶段 3 委托凭据打通后放开 |
| R9 | 飞书接口权限（通讯录 scope）申请周期不可控 | groups claim 是 P2；P1 不依赖它，MVP 可先行上线 |

## 验收清单（阶段 1）

- [ ] 新装 sensteed：扫码 → 自动进系统，全程用户不输入/不见 key；重启无感进入
- [ ] 模型切换协议（chat-completions / messages）与模型下拉正常，目录来自 `/v1/models`
- [ ] 启用的插件 MCP 全部连通（`https://ixicai.cn/mcp/*`，Bearer 自动携带）
- [ ] models Web 可见该用户 key、用量按 key/人归因、配额告警生效
- [ ] Web 吊销 key → 桌面 401 → 重新扫码自动恢复
- [ ] yootun 品牌：激活弹窗与现状一致，回归通过
- [ ] `corepack pnpm check` 全绿；models / sso 仓库各自门禁通过
